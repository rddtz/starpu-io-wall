*** 22-10-2026: Measure mmap I/O outside StarPU time
Goal: measure how much of the mmap I/O happens after the StarPU tasks end
(kernel writeback), which the StarPU trace does not see. Idea: eBPF on the
kernel block/writeback tracepoints.

**** Check if eBPF can be used on PCAD                                :AI:
Read-only probe on =cei2= (no =sudo=, to avoid admin mail): user/caps,
=unprivileged_bpf_disabled=, =perf_event_paranoid=, BTF, kernel config,
tracefs, tools, fallback files (=/proc/meminfo=, =/sys/block/*/stat=),
=vm.dirty_*=, and a real =bpftrace= attempt via =nixw= (2 s count of
=block_rq_issue=). Output is small, so it is printed directly (no =$SCRATCH=).

#+begin_src slurm :host pcad :partition cei :nodelist cei2 :ntasks 1 :cpus 1 :mem 4G :time 00:20:00 :errors yes :job-name ebpf-check
export PATH=$HOME/bin:$PATH
s() { echo; echo "== $*"; }

s host;            hostname; uname -r; id
s groups-sudo;     getent group sudo wheel
s caps;            grep -E '^Cap(Prm|Eff|Bnd)' /proc/self/status
s unpriv_bpf;      cat /proc/sys/kernel/unprivileged_bpf_disabled
s perf_paranoid;   cat /proc/sys/kernel/perf_event_paranoid
s kptr_restrict;   cat /proc/sys/kernel/kptr_restrict
s btf;             ls -l /sys/kernel/btf/vmlinux
s kconfig;         grep -E 'CONFIG_(BPF_SYSCALL|BPF_EVENTS|BPF_JIT|DEBUG_INFO_BTF|FTRACE)=' /boot/config-$(uname -r)
s tracefs;         ls -ld /sys/kernel/tracing /sys/kernel/debug/tracing 2>&1
                   ls /sys/kernel/tracing/events/block 2>&1 | head
s tools-system;    command -v bpftrace bpftool perf 2>&1
s scratch-dev;     df -T "$SCRATCH"; lsblk -o NAME,MODEL,ROTA,LOG-SEC,PHY-SEC
s fallback-read;   grep -E '^(MemTotal|Dirty|Writeback):' /proc/meminfo
                   for d in /sys/block/sd*; do echo "$d: $(cat $d/stat)"; done
s vm-dirty;        sysctl vm.dirty_ratio vm.dirty_background_ratio vm.dirty_expire_centisecs vm.dirty_writeback_centisecs

s bpftrace-try
nixw nix shell nixpkgs#bpftrace -c bpftrace -e \
  'tracepoint:block:block_rq_issue { @n = count(); } interval:s:2 { exit(); }' 2>&1 | tail -20
echo "exit=${PIPESTATUS[0]}"
#+end_src

**** Why it doesn't work by itself right now


Dei uma olhada aqui com o amigo para verificar se de fato não tinha
como sem setuid e de fato o eBPF não funciona por falta de
permissão. O kernel (Linux 6.1.0-45) suporta eBPF mas três coisas
bloqueiam o uso do eBPF: O sysctl =kernel.unprivileged_bpf_disabled=
está em 2, o que faz a syscall bpf() recusar a criação de mapas e o
carregamento de programas para quem não tem =CAP_BPF= ou =CAP_SYS_ADMIN=
(https://docs.kernel.org/admin-guide/sysctl/kernel.html#unprivileged-bpf-disabled
e função __sys_bpf em
https://github.com/gregkh/linux/blob/linux-6.1.y/kernel/bpf/syscall.c#L4981C12-L4981C21. O
código do kernel 6.1 exige, para programas do tipo tracepoint, kprobe
e perf_event, as capabilities CAP_BPF e CAP_PERFMON (ou
CAP_SYS_ADMIN), e isso vale independentemente do sysctl
(https://man7.org/linux/man-pages/man7/capabilities.7.html). Eu não
tenho nenhuma capability (CapEff = 0) nem acesso ao sudo, e o tracefs
(/sys/kernel/tracing) só é acessível pelo root. Mudar o sysctl para 0
não resolveria, porque sem capabilities só são permitidos programas de
filtro de socket (BPF_PROG_TYPE_SOCKET_FILTER e
BPF_PROG_TYPE_CGROUP_SKB), que não servem para rastrear I/O
(bpf_prog_load em
https://github.com/gregkh/linux/blob/79807e970724c1f90cee1316361d61b80db4eef6/kernel/bpf/syscall.c#L2547-L2555;
https://man7.org/linux/man-pages/man2/bpf.2.html).

Para tornar isso possível, o processo que carrega o programa eBPF
precisa ter CAP_BPF e CAP_PERFMON. Como tu disse, um script shell não
serve, porque o Linux ignora o bit set-user-ID em scripts (seção
Interpreter scripts em
https://man7.org/linux/man-pages/man2/execve.2.html#VERSIONS). Por
isso é preciso um executável binário, e só o root pode conceder as
capabilities a esse arquivo (com setcap, que exige CAP_SETFCAP;
https://man7.org/linux/man-pages/man8/setcap.8.html e
https://man7.org/linux/man-pages/man7/capabilities.7.html) ou torná-lo
setuid root. A segunda opção daria root completo ao processo, então a
primeira é a mais restrita.

Vou seguir com o que falamos de escrever um executável em C com libbpf
e com o programa eBPF embutido no binário. Esse programa ficaria preso
apenas aos tracepoints de I/O necessários (block e writeback),
aceitaria só parâmetros simples e validados, como dispositivo e
duração, e salvaria os eventos. Eu vou testar localmente no meu
notebook Debian para checar que está pegando os dados necessários
antes de ir para o PCAD. No PCAD teria que compilar e instalar o
binário como root em um diretório do sistema, e aplicar setcap
cap_bpf,cap_perfmon+ep
(https://man7.org/linux/man-pages/man8/setcap.8.html) ao invés de dar
setuid root para ter zero trust e menor privilégios.

**** Parallel write test on PCAD                                       :AI:
Code in =pwrite-test/= (=buffered_*=, =direct_*=, =direct_unaligned=, =Makefile=).
8 workers write interleaved blocks at known offsets (=lseek= + =write=),
then the file size and every block are checked (=OK= / =CORRUPTED=).
Runs on node-local =$SCRATCH=; only the log goes back to =$HOME=.

Copy sources to PCAD:
#+begin_src sh

#+end_src

#+begin_src slurm :host pcad :partition cei :ntasks 1 :cpus 8 :mem 8G :time 00:30:00 :errors yes :job-name pwrite-test

***** 1. What the application does
- Forward step of RTM (Fletcher 2009): propagates two coupled waves
  =p= and =q= in a 3D ISO/VTI/TTI medium.
- Volume width =W = nx + 2*absorb + 2*4= (main.c:369), split in =C^3=
  cubes (=C= = =width_in_cubes=) of width =w = W/C= (main.c:375). Each
  cube is one StarPU block handle.
- Three time levels per wave: =[0]= = t (being written), =[1]= = t-1,
  =[2]= = t-2, rotated each step (main.c:47-52, 742-743).

***** 2. How the tasks are defined
Three codelets, all static structs in =src/main.c=:

| codelet                       | where      | buffers                          | function                        | def           |
|-------------------------------+------------+----------------------------------+---------------------------------+---------------|
| =insert_perturbation_codelet= | CPU        | 2 RW (p, q of source cube, t-1)  | =perturbation_kernel= kernel.c:276 | main.c:115-123 |
| =rtm_codelet=                 | CPU / CUDA | 52 (10 R medium; p,q: W + 19 R + R) | =rtm_kernel= kernel.c:41 / CUDA | main.c:146-244 |
| =dump_block_codelet= (I/O)    | CPU only   | 1 R (p cube at t)                | =dump_block_kernel= main.c:72-81 | main.c:103-108 |

Submission per time step, time loop main.c:555-746:
1. =wave_insertion= task on the source cube (main.c:562-578).
2. For each cube: register new =[0]= handles with =home_node = -1=
   (StarPU allocates the memory, main.c:587-595), then submit one
   =wave_propagation= task (main.c:597-717).

   per cube (main.c:724-730).
4. =unregister_submit= of the =[2]= handles (main.c:732-739), rotate.

(sequential consistency) [V: no =starpu_task_declare_deps= in the code].

***** 6. How mmap masks I/O
Linux behaviour [general Linux semantics, refs: mmap(2), msync(2),
kernel doc admin-guide/sysctl/vm.rst; not verified on our machine]:
- First store to a page of a =MAP_SHARED= mapping -> page fault, kernel
  gets a page-cache page (fallocated extents are "unwritten", read as
  zeros, no disk read). The page becomes dirty.
- Kernel flusher threads write dirty pages to disk asynchronously
  (=vm.dirty_writeback_centisecs=, =vm.dirty_expire_centisecs=,
  =vm.dirty_background_ratio=).
- =munmap= and =close= do NOT force writeback. Dirty pages stay in the
  page cache and can reach the disk after the process exits.
- If dirty memory passes =vm.dirty_ratio=, the writing thread is
  throttled inside the page fault (=balance_dirty_pages=): only then
  the disk cost shows up inside the =write_block= task.

Consequences [H, to be measured]:
- A =write_block= task mostly measures memcpy + page faults, not disk.
- "Computation Elapsed time" (main.c:553 to 751) ends at
  =starpu_task_wait_for_all=, before =munmap/close= and without
  =msync=: real disk writeback may happen outside the timed region or
  after the program ends. The current metric can undercount I/O.
- The "I/O Wall" should appear when the output volume no longer fits
  under the dirty limits / free RAM, or when writeback is forced.

***** 7. How to do it without mmap (proposals)
1. =pwrite= per x-row: =w^2= calls of =w*4= bytes per cube. Simple, many
   syscalls.
2. Per-cube contiguous layout (cube-major file): one =pwrite= per cube;
   needs reordering for Madagascar (header already stores =seg=,
   main.c:818).
3. =O_DIRECT|O_DSYNC= (the commented code io.c:192-211): bypasses page
   cache, exposes real disk latency inside the task. Needs alignment
   (=statx STATX_DIOALIGN=, io.c:178).
4. Asynchronous: =io_uring= / POSIX AIO, or StarPU out-of-core disk
   nodes (=starpu_disk_register=) [check StarPU 1.4 docs].
5. Keep mmap, add =msync(MS_SYNC)= / =fsync= at the end (or per step) to
   make the real cost measurable. Good first experiment.

*Title:* Beyond the I/O Wall: Hiding I/O Latency in Task-Based Runtime Systems

*Brief:*
In traditional parallel applications (MPI+OpenMP), I/O operations
typically block the execution, stalling computation until they
complete. In task-based runtime systems such as StarPU, dynamic and
asynchronous scheduling of the task dependency graph allows I/O
operations to overlap with other computational tasks, masking part of
this cost. This work investigates how far this masking can actually
holds in I/O-bound applications running on StarPU, points where this
masking effect reaches its limit (the so-called "IO Wall"), and
proposes/evaluates strategies within StarPU's task-based model to
mitigate this limit when possible.
